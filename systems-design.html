How I approach it

The pattern that shows up in almost everything I build is that I start with one flexible system and then express as many mechanics through it as the schedule allows. It's usually cheaper, it keeps the game feeling coherent, and it means new content becomes a designer task instead of a programmer task.

I design systems with the intent of building them myself, so I tend to think about the data layout and the edge cases at the same time as the player experience. That has kept my designs realistic about what a small team can actually finish.

Trash

Trash

Unity · Team of 3 · Dec 2025 to Feb 2026
  • Built a ScriptableObject-driven framework covering every object the vacuum can interact with, so new types are defined as data instead of code.
  • Designed the quota system around a percentage of spawned trash, an in-world time limit, early submission bonuses, strikes, and soft and hard fail states.
  • Designed the vacuum gun as layered states, where suction, clogging, inventory space, and firing speed all push against each other.
  • Built the upgrade loop that turns completed quotas into credits and new mechanics.
